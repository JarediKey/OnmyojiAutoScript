# 道馆调度

[English](README.md)

当天可用的轮次结束或跳过当天时，道馆使用原有的通用调度器。
`scheduler.server_update` 不为 `09:00:00` 时，任务排到 `scheduler.delay_date`
个自然日后的该时间，再加上零至 `scheduler.float_time` 的一次随机延迟。
每天运行时，将 `delay_date` 设为 `1`。共享日期函数仍保留晚间随机延迟最晚至
23:50 的限制。原有的 `09:00:00` 特殊逻辑保留：完成后按当前任务的开始时间加
`success_interval` 和随机延迟安排，不会固定排到次日 09:00。

当 `daily_attack_count` 为 `2` 且游戏显示还剩一次机会时，下次运行时间为当前任务
结束时间加 `scheduler.failure_interval`。这次重试不额外添加随机延迟，也不受每日
固定时间覆盖。第二轮是一次独立的任务运行；如果其他任务正在执行，实际启动时间
可能延后。两轮间隔应留出足够时间，让第二轮在游戏每日重置前完成。

道馆尚未开启时，如果检查发生在每日固定时间之前，就排到当天该固定时间；从固定
时间起至两小时内，按 `failure_interval` 重试；超过两小时后仍未开启，则安排下一次
每日运行。原有的“只在周一到周四开启道馆”选项、战斗及剩余次数识别逻辑仍决定任务
是否可执行、是否存在第二轮。

开启 `try_start_dokan` 后，每个允许执行的日期，只要进入选择对手界面且还有挑战
次数，都会先尝试建立本寮道馆，再选择对手。不再限制周一，也不记录每天只尝试一次；
再次进入该流程（包括第二轮）仍可能尝试建立。道馆已经建立时，沿用现有建立流程的
界面等待及超时处理。勾选“只在周一到周四开启道馆”时，周五至周日仍会在建立及战斗
之前退出。

## 配置示例

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `attack_count_config.daily_attack_count` | `2` | 有机会时进行第二轮 |
| `scheduler.server_update` | `05:00:00` | 每日基准时间 |
| `scheduler.delay_date` | `1` | 当天结束后安排到下一个自然日 |
| `scheduler.float_time` | `00:30:00` | 下次每日开始时间增加 0–30 分钟随机延迟 |
| `scheduler.failure_interval` | `00 00:10:00` | 第二轮或开启失败重试前等待 10 分钟 |

使用这组配置时，第一轮若在 05:20 结束，第二轮就排到 05:30；第二轮结束后，
下一次每日运行排在次日 05:00 至 05:30 之间。时间以任务进程的时钟为准。

首次使用时，将 `scheduler.next_run` 设为预期的首次开始时间。修改间隔或每日固定
时间不会重新计算已经保存的 `next_run`；这一调度方法也不会阻止明确要求的提前运行。

## 离线验证

在仓库根目录运行 `python -m unittest discover -s tests -p 'test_dokan_schedule.py'`。
测试在受控时钟和内存配置下执行实际的道馆调度方法、任务封装、共享日期函数和调度器，
覆盖两轮流程、每日随机延迟上下界、原有的 09:00 特殊逻辑、开启重试、跳过当天及每日一轮设置。
这些测试不运行模拟器，也不验证游戏界面识别。
